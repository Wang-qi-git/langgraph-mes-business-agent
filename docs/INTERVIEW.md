\## 一、电梯演讲（1 分钟版）



> \*\*"我做了一个面向制造业 MES 领域的业务分析 Agent。\*\*

>

> \*\*核心能力\*\*：用户用自然语言问"工单 WO-xxx 什么状态"，Agent 能在 1\~3 秒内从 MES 系统返回实时数据；问"8D 报告 D4 怎么做"，则从知识库检索规范输出结构化答案。

>

> \*\*技术栈\*\*：LangGraph 六节点工作流 + RAG 检索 + DeepSeek LLM + FastAPI + Streamlit + Docker。

>

> \*\*工程完整度\*\*：JWT 认证、多会话隔离、Prometheus 监控、单元测试、GitHub Actions CI、Docker Compose 一键部署。

>

> \*\*数据\*\*：评估集 20 用例，answer\_score 0.96 / rag\_score 0.67，是历史最高版本。"

\## 二、6 个 STAR 故事



\### 📖 故事 1：性能优化（55s → 1.06s）



\*\*S（背景）\*\*

> 项目初期响应延迟高达 55 秒，用户点击后等一分钟才有反馈。



\*\*T（任务）\*\*

> 定位真正的性能瓶颈，而不是盲目调参。



\*\*A（行动）\*\*

> 1. \*\*用 LangSmith Trace 拆解节点耗时\*\*，发现 96% 时间花在模型冷加载，不是 LLM 推理

> 2. \*\*模型预热\*\*：把加载从"用户请求懒加载"挪到"服务启动预热"

> 3. \*\*快速模式跳过 Reranker\*\*：bge-reranker-v2-m3（568M 参数）CPU 上精排 30s，快速模式改向量 Top-2



\*\*R（结果）\*\*

> 快速模式 55s → \*\*1.06 秒（首字 0.74s）\*\*。\*\*定位瓶颈比调参重要 100 倍。\*\*



\---



\### 📖 故事 2：BOM V99 幻觉修复



\*\*S（背景）\*\*

> 用户问"BOM 版本 V99"（不存在），Agent 幻觉输出 7000+ 字报告。



\*\*T（任务）\*\*

> 让 Agent 识别"版本不存在"，但不能误伤其他用例。



\*\*A（行动）\*\*

> 1. \*\*第一次尝试\*\*：加 Prompt 规则 → 5 用例 0.53→0.87 ✅，但\*\*全量 20 用例 0.90→0.70\*\* ❌

> 2. \*\*最终方案\*\*：回退 Prompt，改用\*\*代码级前置守卫\*\*（正则提取版本号 + 与知识库对比）



\*\*R（结果）\*\*

> case\_018 从 0.67/0.33 → \*\*1.0/1.0\*\*，全量\*\*零退化\*\*。

>

> \*\*核心教训：5 个用例能验证方向，只有全量才能验证稳定性。确定性问题用代码拦截，概率性问题才交给 LLM。\*\*



\---



\### 📖 故事 3：双进程架构重构



\*\*S（背景）\*\*

> 加完预热后本地正常，但 Streamlit 页面每请求 36s——它每次交互 rerun 脚本，模块缓存被重置。



\*\*T（任务）\*\*

> 让 Streamlit 不再重新加载模型。



\*\*A（行动）\*\*

> 尝试 `@st.cache\_resource`、`st.session\_state` 均不稳定。最终改为 \*\*FastAPI 后端 + Streamlit 前端\*\*双进程架构：

> - FastAPI 常驻进程，启动时预热

> - Streamlit 只做 UI，HTTP 调用后端



\*\*R（结果）\*\*

> Streamlit 秒开，请求稳定 1\~3s。\*\*核心教训：Streamlit 不适合做重计算，重活交给独立后端进程。\*\*



\---



\### 📖 故事 4：容器化踩坑（24s → 3s）



\*\*S（背景）\*\*

> Docker Compose 编排 5 个服务后，前端查 MES 每次要 24 秒。



\*\*T（任务）\*\*

> 定位容器环境下的性能问题。



\*\*A（行动）\*\*

> 1. \*\*容器里 `127.0.0.1` 不是宿主机\*\* → 改 `mes\_tools.py` 用容器服务名 `http://mock-mes:8001`

> 2. \*\*容器每次重新下载 Embedding 模型\*\* → 挂载宿主机 HF 缓存 + 开 `HF\_HUB\_OFFLINE=1`



\*\*R（结果）\*\*

> 24s → \*\*3.09 秒\*\*。\*\*核心教训：容器化时，凡是运行时下载的外部依赖，都要挂载或预置到镜像。\*\*



\---



\### 📖 故事 5：CI 修复经验



\*\*S（背景）\*\*

> 加 GitHub Actions 后，本地 15 个测试全过，CI 上 5 个失败：`No module named 'fastapi'`。



\*\*T（任务）\*\*

> 搞清楚为什么本地过、CI 挂。



\*\*A（行动）\*\*

> 我本地 venv 装了 fastapi，但 workflow 只装了 pytest + pyjwt + requests。`auth.py` 里 `from fastapi import Depends`，5 个测试全挂。



\*\*R（结果）\*\*

> 加 fastapi 后 CI 变绿。\*\*核心收获：CI 的价值不是"验证本地能跑的代码"，而是捕捉本地环境掩盖的依赖问题。\*\*



\---



\### 📖 故事 6：测试策略（不追 100%）



\*\*S（背景）\*\*

> 单元测试覆盖率只有 8%——因为最大文件 `graph\_agent\_skeleton.py`（748 行）没测。



\*\*T（任务）\*\*

> 要不要为覆盖率硬测那 748 行？



\*\*A（行动）\*\*

> \*\*故意不测\*\*。因为：

> - 测它会触发 50s 模型加载，成本极高

> - UI 代码天天改，测了跟不上

> - 脚本跑一次就完，不需要长期保护

>

> \*\*分层策略\*\*：核心业务（auth 84%、session 97%）+ 重要工具（mes\_tools 46%）+ UI/脚本/模型加载不测。



\*\*R（结果）\*\*

> \*\*核心收获：覆盖率是"防止遗漏"，不是"证明质量"。抓重点，不追数字。\*\*

\## 三、常见问题回答



\### Q1: 为什么不直接用 MES 系统查询？



> "查单字段场景，直接查 MES 更快。但 Agent 的价值在三个场景：

>

> 1. \*\*跨系统聚合\*\*：'工单能不能按期交付'需要查 MES 进度 + WMS 库存 + 设备报警 + 质量异常，人工要 5\~10 分钟切 4 个系统

> 2. \*\*自然语言\*\*：车间主任不记得工单号格式，销售不懂字段名

> 3. \*\*知识+数据融合\*\*：'良率 98.2% 符合规范吗'需要实时数据 + 文档规范 + 推理

>

> \*\*我的定位是'MES 的智能入口'，不是替代品。\*\* 这也是我做快速/深度双模式的原因——简单问题快速，复杂分析深度。"



\### Q2: 模型挂了怎么办？



> "我做了三级降级策略：

> - \*\*一级\*\*：Reranker 正常，精排 Top-3

> - \*\*二级\*\*：推理异常，降级到向量 Top-K

> - \*\*三级\*\*：加载失败，永久标记 `\_RERANKER\_FAILED=True`，避免反复尝试拖慢请求

>

> 实测模型不可用时，服务仍能正常响应，只是精度略降。"



\### Q3: 为什么要双进程架构？



> "Streamlit 的执行模型是'每次交互 rerun 整个脚本'，导致模块级缓存被重置，每次请求都重新加载 50s 的模型。我试过 `@st.cache\_resource` 等方案都不稳定。

>

> 最终改成 FastAPI 后端 + Streamlit 前端，模型隔离在常驻进程，Streamlit 只做 UI，彻底解决问题。"



\### Q4: 怎么保证改动不引入回归？



> "\*\*每次改动后跑全量 20 用例\*\*。我在 BOM V99 修复时踩过坑——5 个用例验证通过，全量却从 0.90 掉到 0.70。

>

> \*\*5 个用例能验证方向，只有全量才能验证稳定性。\*\* 我现在有个硬性规则：涉及 Prompt 或核心逻辑改动，必须跑全量。"



\### Q5: 测试覆盖率为什么只有 8%？



> "整体 8% 是有意识的选择。我按\*\*分层策略\*\*：

> - 核心业务：`auth.py` 84%、`session\_store.py` 97%——这两个模块出 bug 会引发安全问题

> - MES 工具：46%，HTTP 异常分支可以补

> - 模型加载、UI、脚本：\*\*故意不测\*\*——748 行的 `graph\_agent\_skeleton.py` 测一次要触发 50s 模型加载，投入产出比极低

>

> \*\*覆盖率是防止遗漏，不是证明质量。抓重点比盲目追 100% 更有价值。\*\*"



\### Q6: 为什么用 LangGraph 而不是自己写流程？



> "LangGraph 的核心优势是 \*\*StateGraph + 条件边\*\*，天然支持 Reflection 循环——我只需要定义'Reflect 节点评估后决定回退还是收敛'，框架自动处理状态传递。

>

> 如果自己写，要处理状态机、循环控制、异常恢复，会重复造轮子。而且 LangGraph 与 LangSmith 无缝集成，方便我做节点耗时分析。"



\### Q7: 项目还有什么不足？



> "三个真实短板：

> 1. \*\*Grafana 仪表盘在容器重建后会丢\*\*——可以改成一个 volume 挂载 dashboard JSON

> 2. \*\*CI 里没加 Docker 构建验证\*\*——如果镜像构建失败不会提前发现

> 3. \*\*单机部署\*\*——大流量场景需要 K8s 多副本

>

> 这些我都知道，只是\*\*优先级不高\*\*。对于一个作品集项目，当前的工程完整度已经足够。"

\## 五、项目亮点速查（面试官问"你的项目有什么亮点"）



1\. \*\*性能\*\*：从 55s 优化到 1s，定位瓶颈而非调参
